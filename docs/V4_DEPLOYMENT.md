# MLO 4.0 deployment and rollback

Use the existing Portainer Git stack after the exact final source checks and
main image publication succeed. The intended image is
`ghcr.io/pierre-2005/study-notifier:v4.0.0`; a Compose reference does not establish
that this tag has been published. Record its immutable digest and both AMD64 and
ARM64 manifests from the actual successful publish job before pulling it.

No production action was taken during development. The owner handles the
Portainer rollout. See the [setup report](V4_SETUP_REPORT.md) for SMTP, optional AI,
calendar and phone checks, and the [verification report](V4_VERIFICATION.md) for
source/fixture evidence.

## 1. Record the current installation

Keep the original stack name, actual prefixed volume name, Git reference
`refs/heads/main`, root `docker-compose.yml`, loopback port
`127.0.0.1:8001:8000`, database `/data/study_notifier.db`, uploads
`/data/mlo_uploads`, Cloudflare configuration and canonical
`https://organizer.overvault.ca`. Do not activate the deferred www hostname.

Record the running image digest before changing it. Record the actual host and
Docker architecture. An ARM64 image requires suitable host/userspace support;
CI's ARM64 QEMU check does not establish compatibility with a 32-bit Pi OS.
Preserve the existing working deployment while resolving an architecture
mismatch; this release does not replace the OS or unrelated homelab services.

Back up the existing environment privately, including `SESSION_SECRET`,
`MLO_CREDENTIAL_KEY`, bootstrap values, SMTP/OAuth secrets and provider callback
configuration. Do not print these values in an issue, commit or shared report.
Existing account hashes, approvals/capabilities and OAuth credentials must remain.

## 2. Make an independent, restorable backup

Quiesce application writes while taking a coordinated snapshot of the database,
attachments and private configuration. For a live SQLite source, use its online
backup API so outstanding WAL transactions are included. A raw copy of only the
open `.db` can omit committed WAL content. A stopped-container volume snapshot
is another option when it includes the matched database/files/configuration.
Keep an independent copy off the original volume and verify it can be restored.

The application additionally creates a checked online
`*.pre-mlo-v4.sqlite.backup` before v4 initialization. This is a one-time safety
snapshot, not a replacement for the operator's backup, uploads or encryption key.
It must not be the only surviving copy.

## 3. Rehearse the actual private copy

The included synthetic rehearsal was generated by the exact released v3.7.1
source commit `6fc0fd97a7085dacad80745973a56dcea8f3e893`. It preserves all 66
original tables, account ownership, settings, finance, encrypted credentials,
private course data, a WAL sentinel and an attachment. This is strong source
migration evidence; it is not a rehearsal of an unseen installation database.

On an isolated staging host, install the release dependencies and use a new,
empty work directory. Disable outbound delivery during rehearsal. Do not mount
the live volume or point staging at the production database. From the release
checkout, with the actual original owner username:

```sh
PYTHONTZPATH='' python -m scripts.rehearse_v37 \
  --source /private/backups/mlo-before-v4.sqlite \
  --work-dir /private/staging/mlo-v4-rehearsal \
  --legacy-owner-username ORIGINAL_OWNER_USERNAME
```

The existing script name is retained for compatibility. It runs the current
initialization path, including v4's additive schema. It opens the source read-only,
creates an online baseline snapshot, migrates a staging copy twice, checks every
original column/row plus integrity/foreign keys, and restores an identical copy.
Review `report.json`; do not continue past a failure by editing the only backup.

For a Windows staging shell, set the same environment before invoking Python:

```powershell
$env:PYTHONTZPATH = ''
$env:MLO_SCHEDULER_ENABLED = 'false'
$env:MLO_CALENDAR_AUTO_SYNC = 'false'
python -m scripts.rehearse_v37 --source 'C:\private\mlo-before-v4.sqlite' --work-dir 'C:\private\mlo-v4-rehearsal' --legacy-owner-username 'ORIGINAL_OWNER_USERNAME'
```

Use a scheduler-disabled staging process against `staging.sqlite`, with auto-sync
and AI disabled and SMTP unset. Preserve the real encryption keys privately only
where needed to verify existing credentials. Test original logins and approvals,
private/shared owner/editor/viewer access, existing Finance and course records,
upload download/hash, saved appearance/navigation, Budget save/reload, notes and
calendar cache. Use controlled external accounts later for live delivery tests.
Do not send rehearsal traffic to production phone topics or other people's mail.

## 4. Verify the release and redeploy the existing stack

1. Confirm the PR's exact final commit has all required regressions and container
   checks green. A passing earlier checkpoint does not cover later changes.
2. Complete the source release/merge step, then wait for **Build and publish MLO
   Docker image** on `main`. It reuses the complete validation workflow before
   publication. Verify the actual tag/digest and AMD64/ARM64 manifests.
3. In the existing Portainer Git stack, update from `main`, pull the published
   image and redeploy. Keep every environment value, path, port and volume above.
   Do not create a second MLO stack, delete a volume or regenerate keys.
4. Run one application/scheduler worker per database. The image includes pinned
   timezone data, Tesseract and Poppler. Keep `PYTHONTZPATH` empty for non-Docker
   runs so host timezone data does not silently replace the selected rules.
5. Verify `/health` and the container's actual `app.meta.APP_VERSION`. Reload the
   web/PWA. Existing tabs/assets retain compatibility while they refresh; the new
   worker caches current static files and removes only old MLO static caches.
6. Check admin/member sign-in, an original Finance value, an original attachment,
   private project denial, shared viewer/editor behavior, calendar refresh/write
   and one controlled personal reminder. Inspect logs for real errors without
   publishing private values. Measure actual Pi memory/OCR behavior.
7. Perform live SMTP/signup/recovery and installed-PWA/phone acceptance from the
   setup report before opening broader registration/use.

The backend version does not replace a Microsoft Store package identity/version.
No Store submission, DNS, tenant registration or production approval status is
claimed by this release.

## 5. Rollback

Before writes resume broadly, stop the new container and preserve the upgraded
DB/uploads for investigation. Restore the matched verified pre-upgrade database,
attachments and private configuration into the original volume, then restore the
recorded stable image digest. SQLite must be closed during replacement. Do not
leave stale, unrelated `-wal` or `-shm` files beside a restored database. Restore
ownership/permissions and start the old image with the unchanged keys/config.
Check integrity, health, login and a representative record/file.

If users have written new data, export/reconcile those changes before restoring
an older snapshot, or those writes would be lost. Do not run destructive down
migrations against the only copy. Retain the failed upgraded snapshot until the
problem is understood. Never delete the original named volume as a rollback step.
